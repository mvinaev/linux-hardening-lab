# 🛡️ Linux Server Hardening Lab (Ubuntu/Debian)

Учебный проект по развертыванию и защите (Hardening) Linux-сервера. 
Цель проекта — отработать на практике принципы минимальных привилегий, защиту сетевого периметра и настройку мониторинга безопасности.

## 📋 Стек технологий
*   **ОС:** Ubuntu Server (или Debian)
*   **Сеть:** `iptables` (вместо UFW для глубокого понимания netfilter)
*   **Удаленный доступ:** OpenSSH, PuTTY (Windows)
*   **Безопасность:** Fail2ban, `sudoers`, `chmod/chown`
*   **Обновления:** `unattended-upgrades`
*   **Управление сервисами:** `systemd`

## 🗺️ Архитектура стенда
Проект развернут на локальной виртуальной машине (VirtualBox).
*   **Хост (Windows):** `192.168.56.1` (используется для администрирования)
*   **ВМ (Ubuntu Server):** `192.168.56.101` (Host-Only адаптер)

## 🚀 Реализованные этапы

### 1. Управление пользователями и правами (Principle of Least Privilege)
*   **`mad`** — основной административный пользователь. Входит в группу `sudo`. Ему разрешено выполнять команды только через `sudo` (вход root по SSH запрещен).
*   **`techik`** — сервисный пользователь для мониторинга. Не имеет прав на повышение привилегий (`sudo`).
    *   Добавлен в группы `adm` и `systemd-journal` для чтения системных логов.
    *   *Настройка прав:* `chmod 700 ~/.ssh` и `chmod 600 ~/.ssh/authorized_keys`.
*   Настроен кастомный файл `/etc/sudoers.d/techik` для разрешения чтения `journalctl` без полного root-доступа.

### 2. Защита SSH (SSH Hardening)
Конфигурация вынесена в отдельный drop-in файл `/etc/ssh/sshd_config.d/99-hardening.conf`:
*   Изменен стандартный порт на **22022**.
*   Отключена аутентификация по паролю (`PasswordAuthentication no`).
*   Разрешен вход **только по ключам** (Ed25519).
*   Запрещен прямой вход под `root` (`PermitRootLogin no`).
*   Настроен белый список пользователей (`AllowUsers mad deploy techik`).

### 3. Настройка файрвола (iptables)
Отказ от UFW в пользу прямого управления `iptables` для понимания работы фильтрации пакетов.
*   **Политика по умолчанию:** `DROP` для входящих (`INPUT`), `ACCEPT` для исходящих (`OUTPUT`).
*   Разрешены: локальный интерфейс (`lo`), установленные соединения (`ESTABLISHED,RELATED`) и порт SSH (`22022/tcp`).
*   Правила сохранены с помощью пакета `iptables-persistent`.

### 4. Защита от брутфорса (Fail2ban)
Настроен мониторинг логов через `systemd`/`auth.log`.
*   Используется `banaction = iptables-multiport`.
*   **Настройки:** бан на 10 минут (`bantime`), после 5 неудачных попыток (`maxretry`).
*   *Troubleshooting:* Если Fail2ban не видит попытки входа, параметр `backend` меняется с `systemd` на `auto` для чтения стандартных логов `/var/log/auth.log`.

### 5. Автоматические обновления безопасности
*   Включен пакет `unattended-upgrades` через `dpkg-reconfigure`.
*   Сервер ежедневно автоматически устанавливает обновления безопасности.

## 🧪 Как проверялась безопасность (Verification)

1.  **Проверка прав:** Попытка прочитать `/etc/shadow` пользователем `techik` выдает `Permission denied`.
2.  **Проверка SSH:** Вход по паролю невозможен. Вход по ключу с порта 22022 работает.
3.  **Проверка Fail2ban:**
    *   С хоста выполнена симуляция брутфорса: `ssh -p 22022 fakeuser@192.168.56.110` (6 раз).
    *   В `fail2ban-client status sshd` появился забаненный IP.
    *   В `iptables -L` появилась цепочка `f2b-sshd`.
    *   Доступ с забаненного IP полностью пропал.
